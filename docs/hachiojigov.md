# 子育て世帯向け 医療・福祉情報ナビ 要件定義書

版：1
作成日：2026-11-06
対象：MVP（八王子市の子育て世帯向け）

## 1. 目的と背景

### 1.1 背景と課題

国や自治体は医療・福祉・子育ての情報を数多く公開していますが、利用者には次のような壁があります。

- 制度が国・都・市に分かれていて、自分の家に関係するものがどれか分からない。何を調べればよいかも分からない。
- 申請に必要なものや締切が分かりにくく、書類をそろえるのが大変。
- 汎用のAIチャットに聞くと、家族の情報を毎回説明しなければならず、答えの根拠も分からない。

### 1.2 目的

国と自治体が公開している医療・福祉・子育ての情報をベクトルDBに集め、世帯ごとに合うものだけをダッシュボードで提示し、出典つきでAIに相談できるスマホ向けPWAを作る。利用者が次の4つをできるようにする。

1. 自分の家に関係する制度を、調べ方を知らなくても見つけられる。
2. 申請に必要な内容・書類・締切を確認し、準備を進められる。
3. 悩みを自由に相談し、公的資料を根拠にした答えを出典つきで受け取れる。

### 1.3 ビジョン

行政の情報と医療・福祉を掛け合わせたソリューションとして、最終的には国民全員が使えるサービスにする。MVPでは対象を絞り、情報収集と回答の質を確かめてから広げる。

### 1.4 差別化のポイント

ChatGPTやClaudeでも相談はできるが、家族の情報を毎回自分で打ち込まないと、自分に合った答えは返ってこない。また、利用者のデジタル活用スキルに応じてプロンプトの質が異なり、安定した回答を得られない。本サービスは世帯の情報を前もって持ち、公的な資料だけを根拠に答える。

1. **出典つきで答えるRAG**：回答や表示する制度には、必ず根拠の公的資料（URL・取得日）を付ける。
2. **複雑な医療費にも対応**：世帯の医療費・薬・助成制度をまとめて管理できる。医療費を手入力で記録し、申請に必要な情報をまとめておける。その情報を基に、申請できる制度の候補を発見したり、その制度の申請に必要な情報をまとめて提示する。
3. **いつでも相談できる窓口**：文字で質問すれば、公的資料を根拠にした答えを出典つきで受け取れる。画像での質問は将来対応とする。

## 2. スコープ

### 2.1 MVPの範囲

MVPは「八王子市に住む、子どもを持つ親、および妊娠中の人」だけに絞る。

| 項目 | MVPでやること | MVPではやらないこと（将来） |
| --- | --- | --- |
| 対象ユーザー | 子どもを持つ親、妊娠中の人 | 高齢者・介護世帯、障害者、単身世帯など全世帯 |
| 対象地域 | 東京都八王子市（現時点の情報） | 他の市区町村・全国 |
| 情報源 | 国（厚生労働省など）・東京都・八王子市の公開ページとPDF | 自治体ごとの自動収集の全国展開 |
| 情報の種類 | 子育て支援策・イベント・施策、子どもの医療費助成、予防接種、外来・救急の案内 | 介護保険、障害福祉など |
| 外部連携 | なし | マイナポータルAPI |
| 画像 | なし（テキストと手入力のみ） | 領収書の写真読み取り、チャットへの画像添付 |

### 2.2 MVPで扱わないこと

- 八王子市以外の市区町村への対応、全国展開
- 子育て世帯以外（なお子育てに対する福祉支援は含む）への対象拡大（介護、障害福祉、高齢者など）
- マイナポータルAPIなどの外部連携（MVPでは医療費データの形を将来の連携に合わせておくだけにする）
- 画像の読み取り・添付（領収書の写真読み取り、チャットへの画像添付）は将来対応とする。
- 妊娠・出産の制度（妊婦健診など）は「子育て」に含める。つまりMVPとして取り扱う。妊娠中の人も登録できる。
- 制度の人による確認は、最初の20〜30制度に限定する。運営者が対象・締切・必要書類を確認した制度に「確認済み」フラグを付け、確認済みの制度のみをダッシュボードの表示とAI回答の根拠に用いる。

## 3. 想定ユーザーとユースケース

想定ユーザーは、八王子市に住む忙しい子育て中の親（妊娠中の人を含む）です。子ども向けの支援策・イベント・施策を調べたいが、何を調べればよいか分からない、というのが一番の悩みです。登録や入力の手間を負担に感じやすいため、最初は最低限の入力で使い始められることを重視します。

| ID | ユースケース | 内容 | 関連機能 |
| --- | --- | --- | --- |
| UC1 | はじめて使う | 会員登録のあと、郵便番号と子どもの人数・年齢（妊娠中なら出産予定日）だけを入れ、すぐに自分の家に関係する制度を見る | F1・F2 |
| UC2 | ダッシュボードを見る | おすすめの制度、進行中の申請の途中経過、締切を確認し、タップして詳細を見る | F4 |
| UC3 | 申請の準備をする | 必要な書類や内容を確認し、必要ならAIに手伝ってもらう | F4・F5 |
| UC4 | AIに相談する | 自由に悩みを入力し、公的資料を根拠にした解決策を出典つきで受け取る。提案された内容をダッシュボードに追加できる | F5 |
| UC5 | 医療費をまとめる | 医療費を手入力で記録し、助成や申請に必要な形でまとめる | F6 |

## 4. 用語

| 用語 | 意味 |
| --- | --- |
| RAG | 検索で取り出した資料を根拠に、AIが回答を作る仕組み |
| ベクトルDB | 文章の意味を数値（ベクトル）にして保存し、意味の近いものを検索できるデータベース |
| チャンク | 公的資料を検索しやすい大きさに分割した断片。出典URLや取得日などを付けて保存する |
| 制度カード | ダッシュボードに表示する、制度1件ぶんの要約 |
| PWA | ホーム画面に追加して、アプリのように使えるWebアプリ |
| 要配慮個人情報 | 障がいの有無など、個人情報保護法で特に慎重な扱いが求められる情報。取得前に本人の同意が必要 |
| 自治体コード | 市区町村を表すコード。情報の絞り込みと、対応自治体の追加に使う |

## 5. 利用の流れ

1. 初めてアプリを開くと、ログイン画面が表示される。サービスの利用には会員登録が必要。
2. 郵便番号を入力し、続けて子どもの人数と年齢を入力する。子どもがいない妊娠中の人は、人数に0を入れて出産予定日を入力する。ほかの項目は「あとで入力する」を選べる（F2）。
3. ダッシュボードに、世帯に合う制度、進行中の申請、締切が表示される。カードをタップすると詳細を見られる（F4）。
4. 詳細画面から「AIに聞く」を押すか、AI相談を開いて自由に質問する。回答には出典が付く（F5）。
5. AIが提案した制度は「ダッシュボードに追加」で反映できる（F5）。
6. 医療費は手入力で記録し、集計と、申請できそうな制度の候補（「対象の可能性」）を確認する（F6）。
7. 急な病気・けがへの対応（F7）はMVPの対象外とする。

## 6. 機能要件

### 6.1 機能一覧

受け入れ条件の詳細（EARS形式）は、別ドキュメント「Kiro用プロジェクト仕様」の4章にあります。

| ID | 機能 | 概要 | 優先度 |
| --- | --- | --- | --- |
| F1 | ユーザー登録・ログイン | 会員登録（Google／メール）してログインする。登録しないとサービスは使えない | 必須 |
| F2 | 初回入力（オンボーディング） | 郵便番号と子どもの人数・年齢（妊娠中は出産予定日）を最小限で入力。残りはあとから追加 | 必須 |
| F3 | 公的情報の収集・更新 | 公的サイトとPDFを定期取得し、出典つきでベクトルDBに保存（運営側）。運営者が確認した制度に「確認済み」を付ける | 必須 |
| F4 | ダッシュボード | 世帯に合う制度の候補、進行中の申請、締切を表示。詳細画面へ | 必須 |
| F5 | AI相談 | 出典つきRAGチャット（テキストのみ）。提案をダッシュボードに追加できる | 必須 |
| F6 | 医療費のまとめ | 医療費を手入力で記録し、集計し、申請に使える形にまとめる | 必須 |
| F7 | 急な病気・けがへの対応 | 夜間の発熱などで、固定の案内・医療機関の地図・持ち物を表示 | MVP対象外（いちど置く） |
| F8 | 締切の通知 | 締切が近い申請や、保存した制度の更新を知らせる | できれば |
| F9 | アカウント削除と世帯情報の管理 | アカウント削除（全データの削除）は必須。世帯情報の編集は「できれば」 | アカウント削除：必須／世帯情報の管理：できれば |

### 6.2 機能ごとの要件

#### F1. ユーザー登録・ログイン
**サービスの利用には必ず会員登録が必要。匿名での利用はできない**
- F1-1　登録・ログインが済んでいないユーザーには、ログイン画面だけを出し、ダッシュボード・AI相談・世帯データを表示しないこと。
- F1-2　Googleアカウントまたはメールアドレスとパスワードで会員登録でき、登録後に初回入力へ進むこと。
- F1-3　ログインの総当たり攻撃への対策は、認証サービスが標準で提供する機能を使うこと。あわせて、APIにユーザー・IPごとのリクエスト上限を設けること。
- F1-4　登録済みユーザーが別の端末でログインしたとき、同じデータを表示すること。

#### F2. 初回入力（オンボーディング）

忙しい親の負担を減らすため、初回に聞くのは最低限にして、残りはあとから追加できるようにする。

| 入力項目 | 初回必須 | あとから追加 |
| --- | --- | --- |
| 住んでいる場所の郵便番号 | する |  |
| 子どもの人数（0〜20人）と年齢（0〜18歳。0歳は月齢でも可） | する |  |
| 出産予定日（今日から10か月以内） | 子どもが0人のときのみ必須 | 子どもが1人以上のときは任意 |
| 子どもの性別 |  | する |
| ユーザー自身の名前・年齢・性別 |  | する |
| 子どもの現在の状況（チップ選択＋自由入力） |  | する |

- F2-1　7桁の郵便番号から都道府県・市区町村・町名を表示し、参照する情報源（国・東京都・八王子市）を示すこと。
- F2-2　八王子市外の郵便番号の場合は「現在は八王子市のみ対応」と伝え、国の制度だけで続けるかを選べること。
- F2-3　存在しない郵便番号は、入力欄のそばにエラーを表示して次へ進ませないこと。
- F2-4　子どもの状況は、「障がいの有無」「サッカーが好き」「留学を考えている」のような一般的な特徴をチップで複数選べ、自由入力もできること。
- F2-5　「あとで入力する」を選んだら、必須項目だけでダッシュボードを作ること。
- F2-6　障がいや妊娠・出産予定日など健康に関わる項目を初めて入力するときは、利用目的を示して同意を得てから保存すること。
- F2-7　子どもの人数が0人の場合は「妊娠中または出産予定」の入力を必須とし、出産予定日は今日から10か月以内の日付だけを受け付けること。子どもの人数が1人以上の場合、妊娠の入力は任意とすること。

#### F3. 公的情報の収集・更新（運営側）

- F3-1　定期的に、登録済みの情報源（八王子市・東京都・厚生労働省などのページとPDF）を取得すること。
- F3-2　取得した内容が前回と同じなら再処理しないこと（ハッシュで判定）。
- F3-3　内容が変わったものと新しいものは、制度ごとの形式的なフォーマット（制度名・対象・内容・申請方法・必要書類・締切・窓口・出典）に整理し、分割・埋め込みを作ってベクトルDBに保存すること。
- F3-4　すべてのチャンクに、出典URL・取得日・自治体コード・対象（年齢帯など）・カテゴリを付けること。
- F3-5　取得に失敗したときは、前回のデータを残したままエラーを記録すること。
- F3-6　情報源のページが削除されたときは、そのチャンクを検索対象から外すこと。
- F3-7　回答の根拠にするチャンクは、公的資料の原文抜粋、出典URL、見出しまたはPDFページ、取得版のハッシュで作ること。AIが整理した構造化情報（制度名・対象・締切など）は表示と絞り込み専用とし、回答の根拠にしないこと。
- F3-8　1回の実行で取得するページは最大100ページ、1つの情報源で取得するPDFは最大10件とし、取得の再試行は最大3回までとすること。
- F3-9　運営者が対象・締切・必要書類を確認した制度に「確認済み」フラグを付け、確認済みの制度だけをダッシュボードの表示とAI回答の根拠に使うこと。確認は最初の20〜30制度に限定してよい。

#### F4. ダッシュボード

- F4-1　世帯情報で絞り込んだ「おすすめの制度」「進行中の申請と途中経過」「締切」を表示すること。年齢区分は候補を探すための大まかな分類として使い、条件が不明な制度は「対象外」にせず「要確認」として含めること。資格の判定は地域・年齢・日付などの条件判定で行い、結果は「対象の可能性」と表示すること（ベクトル検索では判定しない）。
- F4-2　各制度カードに、国・都・市のどれの制度か、対象の家族、一行の要約、出典と更新日を表示すること。
- F4-3　カードをタップすると、詳細画面（要点、手続きの流れ、必要なもののチェックリスト、窓口、出典一覧）を表示すること。
- F4-4　詳細画面の「AIに聞く」で、その制度を話題にしたチャットを開始し、申請内容の記入を補助すること。
- F4-5　申請を「進行中」にしたら、その申請の締切とやることをダッシュボード上部に表示すること。
- F4-6　カテゴリで絞り込んだら、該当する制度だけを表示すること。

#### F5. AI相談（出典つきRAGチャット）

- F5-1　質問を送信したら、確認済みの制度のチャンクを世帯情報（自治体・子どもの年齢区分など）とカテゴリで絞り込み、そのあとでベクトル検索を行い、その結果だけを根拠に回答すること。ベクトル検索は関連資料の探索のみに使い、利用資格の確定には使わない。
- F5-2　回答本文に \[1\] のような引用番号を入れ、その下に出典（資料名・URL）を表示すること。
- F5-3　引用番号が検索結果に存在しないチャンクを指していたら、引用を黙って消さずに1回だけ再生成すること。それでも検証できないときは、その回答を事実として表示せず、「根拠を確認できませんでした」と、取得した出典の一覧と問い合わせ窓口を表示すること。あわせて、回答の各主張が引用したチャンクの範囲内かを確認すること。
- F5-4　関連する公的資料が見つからないときは、推測で答えず、「資料が見つからない」と伝えて問い合わせ先を案内すること。
- F5-5　質問はテキストのみとする。画像の添付はMVPの対象外（将来対応）。質問文は最大500文字とし、入力欄に「氏名や病歴などの個人情報は入力しないでください」と常に表示すること。
- F5-6　回答で制度を提案したら「ダッシュボードに追加」ボタンを表示し、押されたら反映すること。
- F5-7　次に聞けそうな質問の候補をチップで表示すること。
- F5-8　病気の診断や治療の判断を求められたときは、診断をせず、医師や相談窓口への相談をすすめること。

#### F6. 医療費のまとめ（手入力）

領収書の写真読み取りはMVPの対象外（将来対応）。医療費は手入力で記録する。

- F6-1　日付・医療機関名・金額・対象者を手入力して保存したら、世帯の医療費記録に追加すること。金額は1〜9,999,999円の整数とする。
- F6-2　保存・修正・削除のたびに、月ごと・年ごと・家族ごとに集計し直すこと。
- F6-3　未入力の項目や範囲外の値があるときは、保存せずに入力欄のそばにエラーを表示すること。
- F6-4　記録が助成や申請の対象になりそうなときは、関係する制度を「対象の可能性」として提示し、必要な情報をまとめて「あとは入力するだけ」の状態にすること。

#### F7. 急な病気・けがへの対応（夜間の発熱など）
**これはMVPでは実装しない。いちど置いておく**
- F7-1　「急な病気・けが」の入口では、AIの生成を使わず、あらかじめ用意した案内（子どもの医療電話相談 #8000、救急相談 #7119、救急車 119、医療機関を探せる公的サービス）を表示すること。
- F7-2　外来を探すときは、現在地または住所の近くの医療機関を地図で示すこと。
- F7-3　受診時の持ち物（マイナ保険証、医療証など）をチェックリストで示すこと。
- F7-4　チャットで緊急性の高い言葉（意識がない、けいれんなど）を検知したら、回答より先に119番などの緊急連絡先を表示すること。

#### F8. 締切の通知（できれば）

- F8-1　進行中の申請の締切が近づいたら、プッシュ通知を送ること（ユーザーが許可した場合のみ）。
- F8-2　公的情報が更新され、ユーザーが保存した制度に変更があったら、アプリ内でお知らせすること。

#### F9. アカウント削除（必須）と世帯情報の管理（できれば）

- F9-1　【できれば】世帯情報を変更したら、ダッシュボードのおすすめを更新すること。
- F9-2　【必須】アカウント削除を実行したら、確認ダイアログのあと、世帯情報・チャット履歴・医療費記録・認証サービス上のアカウントをすべて削除すること。

## 7. データ要件

### 7.1 扱うデータ

| データ | 主な項目 | 閲覧・更新できる人 |
| --- | --- | --- |
| 世帯情報 | 郵便番号、自治体コード、保護者の属性（任意）、妊娠の情報（出産予定日）、同意の記録 | 本人のみ |
| 子どもの情報 | 年齢（または生年月）、性別（任意）、状況チップ、自由入力 | 本人のみ |
| 申請状況 | 制度ID、状態（未着手・進行中・完了）、締切、やること | 本人のみ |
| 医療費記録 | 日付、医療機関名、金額、対象者（すべて手入力。画像は扱わない） | 本人のみ |
| チャット履歴 | 役割、本文、引用したチャンク | 本人のみ |
| 制度情報 | 制度名、対象、内容、申請方法、必要書類、締切、窓口、年齢区分、自治体コード、レベル（国・都・市）、確認済みフラグ。AIが整理した構造化情報で、表示と絞り込み専用 | 確認済みの制度のみ閲覧可。更新は収集系のみ |
| チャンク | 公的資料の原文抜粋、埋め込みベクトル、制度ID、出典URL、見出しまたはPDFページ、取得日、取得版のハッシュ、埋め込みモデル名・次元数・版など | APIと収集系のみ |
| 情報源 | 情報源URL、自治体コード、取得頻度、前回のハッシュと取得日時 | 収集系のみ |

### 7.2 公的情報に付けるメタデータ

出典URL、取得日、自治体コード、レベル（国・都・市）、対象（年齢区分）、カテゴリ、ハッシュ、見出しまたはPDFページ。年齢の範囲は、検索で絞り込みやすいよう区分のタグで持たせる。読み取れない年齢区分は「不明」とし、絞り込みで落とさない。

### 7.3 保持と削除

- アカウントを削除したら、世帯情報・チャット履歴・医療費記録・認証サービス上のアカウントをすべて削除する（MVPの必須機能）。
- 画像は扱わないため、画像の保存期間は定めない。

## 8. 非機能要件

### 8.1 プライバシー・セキュリティ

- 障がいの有無や妊娠・出産予定日などは個人情報保護法の「要配慮個人情報」にあたるため、取得前に本人の同意を得る。利用規約とプライバシーポリシーを用意する。
- ユーザーデータは、本人しか読み書きできないよう制限する。
- 世帯情報・医療費記録・チャット履歴などのユーザーデータは日本国内（東京リージョン）に置く。認証情報（メール、認証ID）の処理は東京以外（米国など）で行われる場合があり、プライバシーポリシーで明示する。
- 世帯プロフィールからLLMへ渡す属性は、自治体と年齢区分のみとする。質問文は、電話番号・メール・郵便番号をマスクしてから送る。氏名や病歴などの自由文の個人情報は除去できないため、入力欄に注意書きを常に表示し、質問は最大500文字とし、外部AI（Vertex AI）へ質問文が送信されること・保持条件をプライバシーポリシーで明示する。
- 画像の読み取り・添付は扱わない（将来対応）。
- APIキーや認証情報はコードに書かず、専用の仕組みで管理する。

### 8.2 AIの安全性

- AIは公的資料にない内容を断定しない。根拠がないときは「分からない」と答える。
- 病気の診断・治療の判断はしない。画面に「診断や治療の判断は医師に」と常に表示する。
- 緊急時の案内（F7）はMVPの対象外。将来実装するときは、AIに生成させず、固定の内容で表示する。
- すべての制度情報に出典と取得日を表示し、「最新の情報は窓口で確認を」と添える。

### 8.3 使いやすさ・アクセシビリティ

- スマホの縦画面（幅390px前後）を基準に設計し、ホーム画面に追加できるPWAにする。
- タップできる部分は44px以上、文字と背景のコントラスト比は4.5:1以上にする。
- 主なメニュー（ホーム・さがす・AI相談・わが家）は画面下部のタブバーに置く。
- 初回入力は最小限にし、「あとで入力する」を選べるようにする。

### 8.4 性能・可用性

- AIの回答はストリーミングで表示し、待ち時間を短く感じさせる。
- 起動済みの状態では、質問の90%で3秒以内に最初のテキスト断片を表示する。初回起動（コールドスタート）では、待機中表示を1秒以内に出し、90%で10秒以内に最初の断片を表示する。実測して評価する。
- 一度開いた制度情報は、電波が弱くても表示できるようにする。

### 8.5 運用・コスト

- 個人開発の予算内（累計20ドル以下）で運用することを設計目標とする。常時起動のサーバーは使わず、使った分だけ課金されるサービスを選ぶ。ただし、これだけで20ドルに収まることは保証されない。運営開始前に、利用人数・試作期間・相談回数を見積もり、20ドルに収まるか確認する。
- 予算アラートを設定する。
- ユーザーごとのAI呼び出し上限（1日20回）、サービス全体の上限（1日500回、設定で変更可）、質問文500文字と回答最大トークン数の上限を設ける。AIと収集処理を止める運営用スイッチを用意する。上限に達したときは、ユーザーに分かりやすいメッセージを表示する。
- 埋め込みモデルを変えたときに既存のチャンクを再生成できるよう、チャンクにモデル名・次元数・版を持たせる。
- 公的情報は定期的に取得し、変更があったものだけを更新する。

### 8.6 拡張性・保守性

- 自治体コードごとに情報源を登録するだけで、対応する自治体を増やせる設計にする。
- AIのモデル名やリージョンはコードに直接書かず、設定に出して差し替えやすくする。

### 8.7 対応環境

- パソコンとスマホのブラウザとPWA。iPhoneのプッシュ通知は、ホーム画面に追加したPWAのみ受け取れる。

## 10. MVPの完了条件（案）

- 八王子市・東京都・国の子育て関連の情報が収集され、出典URLと取得日つきで検索できる。
- AI相談の回答すべてに出典が付き、引用番号が検索結果と一致する。
- 質問と期待する出典の評価セット（20問程度）で、回答の質を確かめている。
- 会員登録のあと、郵便番号と子どもの年齢（妊娠中なら出産予定日）だけでダッシュボードが表示される。
- 確認済みの制度（最初の20〜30制度）だけが、ダッシュボードの表示とAI回答の根拠に使われている。
- 評価セットで、「必要な資料が検索されるか」と「回答が資料の範囲を超えないか」を分けて評価している。
- アカウント削除で、全データが削除される。
- 必須機能（F1〜F6、およびF9のアカウント削除）の受け入れ条件を満たしている。F7はMVPの対象外とする。

## 11. リスクと対策

| リスク | 対策 |
| --- | --- |
| 公的情報が古い・誤って取り込まれる | 差分取得と定期更新。すべての情報に出典と取得日を表示し、「最新は窓口で確認を」と添える |
| AIが根拠のない回答や医療判断をしてしまう | 検索結果だけを根拠にし、引用を検証する。診断はしない。見つからないときは「分からない」と答える |
| 緊急時に誤った案内をしてしまう | MVPでは緊急時の案内（F7）を扱わない。将来は、AIの生成を使わず、固定の案内を表示する |
| 要配慮個人情報の取り扱い | 同意の取得、本人のみ読み書きできる制限、ユーザーデータは東京リージョン（認証情報を除く）、世帯プロフィールから渡す属性は自治体と年齢区分のみ、質問文のマスクと注意書き、画像は扱わない |
| 質問文に氏名や病歴が含まれる | 入力欄の注意書き、最大500文字、プライバシーポリシーで外部AIへの送信と保持条件を明示 |
| 制度の確認が追いつかない | 確認済みの制度（最初の20〜30制度）だけを表示と回答の根拠に使う |
| 自治体を増やすときの収集・更新の手間 | 自治体コードごとに情報源を登録するだけで増やせる設計にする。まず八王子市で質を確かめる |
| 利用料金が増える | 使った分だけ課金されるサービスを選び、予算アラートとAI呼び出しの上限、運営用スイッチを設ける。運営開始前に利用額を見積もる |

## 12. 開発の進め方

「資料を集める」→「根拠つきで答える」→「世帯に合わせて見せる」の順に作る。RAGの回答の質を早めに確かめるため、画面より先に情報収集を作る。

1. フェーズ0：土台（Google Cloudプロジェクト、予算アラート、開発環境、セキュリティ関連のテストとCI。`main` への直接コミット禁止、コミット規約は docs/commit-convention.md に従う）
2. フェーズ1：情報の収集（F3）
3. フェーズ2：出典つきRAG（F5の中心。評価セットで回答の質を測る）
4. フェーズ3：アプリ画面（F1・F2・F4・F5、PWA対応）
5. フェーズ4：医療費（F6、手入力）とアカウント削除（F9）。F7と画像つきの質問はMVPの対象外
6. フェーズ5：仕上げ（F8、F9の世帯情報の管理、利用規約・プライバシーポリシー・同意画面）
